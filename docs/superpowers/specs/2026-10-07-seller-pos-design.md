# Второй этап MyStore: кабинет продавца и кассовые операции

Дата: 7 октября 2026. Статус: утверждено владельцем продукта 7 октября 2026.
Основание: согласованное ТЗ MyStore и реализованное ядро первого этапа (PR #1).
Это детализация следующего этапа разработки, а не изменение общей модели маркетплейса.

## Цель и границы

Сотрудник входит через браузер, выбирает доступный магазин, создаёт учётную позицию, принимает товар сканером и продаёт его в открытой смене. Сервер подтверждает документы и обновляет остатки; возврат связан с исходной продажей.

Из пожеланий пользователя: обычный сканер без экрана подключается к ноутбуку; он работает и на приёмке, и на продаже. Основной интерфейс площадки для покупателей остаётся публичным магазином нескольких продавцов. Кабинет размещается под /seller и не подменяет будущую главную страницу.

Предлагаемые технические решения этого этапа: React + TypeScript + Vite в apps/web, один источник данных NestJS/PostgreSQL, одна касса на магазин, русский интерфейс, KGS, отображение времени Asia/Bishkek. Работа требует сети. Фото, принтер, публичная витрина и онлайн-заказы сохраняются для следующих этапов.

## Выбор подхода

Рекомендуется браузерный кабинет и расширение текущего API. Это использует уже проверенные транзакции и позволяет подключить сканер как клавиатуру.
Альтернатива — сначала интерфейс к текущим API без смен и возвратов: быстрее, но не завершает кассовый сценарий.
Отдельное настольное приложение лучше подходит для прямого управления оборудованием, однако усложнит установку; оно не требуется для USB-сканирования.

## Экраны и права

Вход; выбор магазина; список товаров с поиском и пагинацией; создание позиции; приёмка; касса; текущая смена; история продаж; возврат по продаже.
Кассир видит товары, доступный остаток, собственную смену и продажи. Себестоимость и приёмка недоступны.
Владелец и менеджер сохраняют права первого этапа. Возврат в этом этапе доступен только владельцу: выдача отдельного разрешения кассиру и настройка финансовых прав менеджера выполняются позже.
Смена принадлежит открывшему сотруднику. Он продаёт и закрывает её; владелец может закрыть чужую смену с обязательным комментарием. Возврат владельцем требует его текущей открытой смены.
Закрытые отчёты смен доступны владельцу и сотруднику этой смены. Проверки выполняются API, включая прямые обращения по чужим идентификаторам.

## Веб-сессия

Добавляется cookie-сессия для браузера с HttpOnly, SameSite=Lax, Secure в production, сроком 12 часов и отзывом при выходе. Bearer-контракт первого этапа сохраняется для существующих клиентов.
Веб и API работают под одним origin: proxy в разработке, единая точка входа при размещении. Изменяющие браузерные запросы проверяют Origin и CSRF-токен, связанный с сессией; разрешены только явно настроенные origins.
Токен авторизации не хранится в localStorage. Ответ /auth/me выдаёт минимальные данные сотрудника и магазины с его ролями.

## Каталог и приёмка

Список возвращает название, код, цену и остатки; закупочные данные выдаются только разрешённым ролям. Денежный ввод в сомах переводится в целые тыйыны без floating point.
Создание позиции использует существующий API и не создаёт приход. После создания пользователь может перейти к приёмке.
Сканирование добавляет одну единицу; повторное сканирование того же варианта увеличивает количество строки. Закупочную цену задаёт уполномоченный сотрудник.
Неизвестный код в приёмке предлагает создание карточки; в кассе показывает ошибку и не создаёт товар.
Редактирование карточек, фото, категории, артикулы и публикация не входят в эту детализацию: используется существующая учётная позиция первого этапа.

## Сканер и черновики

Поддерживается USB HID scanner с суффиксом Enter. Код читается как строка с сохранением ведущих нулей. Отдельное поле сканирования имеет явный фокус и доступно для ручного ввода.
Сканирование не перехватывает набор в остальных полях. Очередь lookup обрабатывает быстрые сканы последовательно; каждое отдельное подтверждение Enter учитывается, одинаковые коды по времени не отбрасываются.
Корзина и приход сохраняются локально отдельно по сотруднику, магазину и типу операции. Выход очищает черновики сотрудника; смена магазина не переносит строки.
До отправки сохраняются ключ идемпотентности и точное тело операции. При неизвестном результате черновик блокируется для изменения; повтор использует тот же ключ и тело.
Сеть отсутствует — проведение недоступно. Сеть восстановилась — пользователь явно повторяет запрос. Автоматическое фоновое проведение запрещено. Успех показывается только после подтверждения сервера.

## Смены и оплата

Для магазина создаётся одна касса. У неё может быть только одна открытая смена, что защищено ограничением БД.
Открытие содержит начальные наличные; закрытие — фактически пересчитанные наличные. Ожидаемые наличные = начальные + наличные продажи − наличные возвраты. При расхождении обязателен комментарий.
Внесения, изъятия, смешанная оплата и несколько касс отложены. При продаже выбирается один способ: наличные или карта; запись означает отметку получения денег сотрудником, без обращения к платёжному провайдеру.
Новый веб-сценарий продажи сохраняет товарный документ, строки оплаты и связь со сменой одной транзакцией. Старый товарный API первого этапа сохраняется как отдельный внутренний контракт; документы без смены явно обозначаются и не включаются в денежные итоги.
Продажа и закрытие блокируют одну запись смены: закрытая смена не принимает последующие операции. Открытие и закрытие также идемпотентны.
История показывает исходные позиции, суммы и возвращённое количество; закупочные снимки скрыты от кассира.

## Возвраты

Возврат указывает исходную продажу, позиции, количество, причину и состояние товара. Общая возвращённая величина не превышает проданную; конкурентные запросы блокируют исходные строки.
Сумма возврата определяется исторической ценой продажи. Себестоимость восстанавливается из исторического снимка: для частичных возвратов используется разница округлённой накопительной стоимости до и после операции. Последний возврат восстанавливает оставшуюся стоимость точно.
Годный товар возвращается в физический и доступный остаток. Брак фиксируется отдельным документом возврата без увеличения доступного запаса; перемещение брака и его последующее списание будут отдельным складским модулем.
Операция фиксирует товарный результат и возврат денег в одной транзакции; способ выплаты выбирается владельцем, наличный возврат уменьшает ожидаемую кассу. Фактическая выплата выполняется сотрудником; платёжный провайдер не вызывается.
Исторические продажи первого этапа допускают товарный возврат, но денежный возврат по ним в этом этапе блокируется, поскольку исходная оплата неизвестна.
Журнал движений остаётся неизменяемым. Дубли, превышение количества и несовпадение магазина отклоняются сервером.

## Структура реализации

apps/web: маршруты продавца, клиент API, формы, очередь сканирования, хранилище черновиков.
apps/api: браузерная авторизация, список магазинов/товаров, кассы и смены, платежные записи, история продаж, возвраты.
Новые таблицы связываются составными ключами с магазином. Деньги — целые тыйыны; расчёты себестоимости через bigint. Идемпотентность использует существующий сервис и распространяется на новые операции.
Новые маршруты /shops/:shopId/pos/* отделяют кассовую продажу от товарной операции первого этапа.
Миграции не изменяют проведённые документы и не придумывают оплаты для существующих продаж.

## Проверка и приёмка

1. Вход, выход, истечение сессии; CSRF и изоляция магазинов проверены прямыми API-запросами.
2. Приход 10, продажа 2, возврат 1 годной единицы дают остаток 9; брак не увеличивает доступность.
3. Три скана одинакового кода дают три единицы; ведущие нули сохраняются. Быстрые сканы не теряются.
4. Кассир не получает закупочные цены в API, HTML или локальном черновике.
5. Повторы после потери ответа не создают вторую продажу, оплату, смену или возврат.
6. Конкурентная продажа последней единицы, превышение возврата, одновременное открытие смен и продажа при закрытии проверяются на PostgreSQL.
7. Расчёты наличных, карточных продаж, возвратов и расхождения совпадают с контрольным набором. Возврат после нового прихода сохраняет историческую себестоимость.
8. Браузерный сквозной сценарий: вход → создание → приход → открытие смены → продажа → возврат → закрытие. Проверяется восстановление черновика после перезагрузки.
9. Формы работают с клавиатуры на ширинах 360, 768 и 1440 px.
10. CI выполняет прежние 40 интеграционных тестов, новые API/UI проверки, сборку и smoke.

Автоматические тесты моделируют ввод USB-сканера. Проверка физического сканера выполняется отдельно на выбранной пользователем модели; её результат не подменяется браузерным тестом.
