# Единый рабочий кабинет MyStore

Дата: 2026-10-13. Основа логики и письменная спецификация согласованы пользователем. План реализации также подтверждён; реализация завершена и проверена локально. Публикация на сайте произойдёт после слияния PR и deployment.

## Задача

Сейчас один пользователь может последовательно видеть «Панель партнёра», «Администрирование» и «Рабочее пространство» с разными меню и подписями роли. Особенно неудобен аккаунт, который одновременно администрирует платформу и владеет магазином. Нужно сделать одну оболочку кабинета: контекст объясняет, какими данными и действиями пользователь управляет, а профиль всегда обозначает один и тот же аккаунт.

Оформление остаётся по `docs/admin-ui-kit.md`: тёмно-зелёное меню, светлая рабочая область, общие карточки, поля, кнопки и отступы из `/platform/admin`.

## Общая оболочка

Все защищённые страницы платформы, магазина и выбора магазинов используют один `WorkspaceShell` с общими брендом MyStore, переключателем контекста, навигацией, верхней панелью, профилем и выходом. Подпись бренда — «Рабочий кабинет».

Профиль показывает email и инициалы аккаунта. Профиль больше не переименовывает человека в «Партнёра», «Админа» и «Владельца» при каждом переходе. Полномочия относятся к выбранному контексту: «Администратор платформы» для платформы, «Владелец», «Менеджер» или «Кассир» для конкретного магазина.

Контекст виден в переключателе и верхней панели. Для магазина всегда показано его имя; для платформы — «Платформа». Общая оболочка сохраняет независимую прокрутку меню и рабочей области на компьютере, нормальную прокрутку страницы на телефоне и существующую печать этикеток.

## Переключение контекста

Список строится только из ответа `/api/auth/me`:

- «Платформа» — только при `platformAdmin=true`.
- «Магазин: <имя>» — для каждого магазина в `user.shops`, с его текущей ролью.
- «Мои магазины» — страница выбора/общего обзора только при нескольких доступных магазинах.

Администратор платформы не получает автоматически кассу или учёт чужого магазина. Для выбора магазина нужна его отдельная membership. Глобальные таблицы администрирования остаются доступны в контексте платформы по существующим полномочиям.

Выбор платформы открывает `/platform/admin`. Выбор магазина открывает его начальный раздел по роли: товары для владельца/менеджера, кассу для кассира. Переключатель доступен на телефоне и компьютере и имеет явную подпись для клавиатуры и экранных дикторов.

При одном доступном магазине отдельная панель партнёра и промежуточный обзор этого же магазина не показываются. При нескольких магазинах страница «Мои магазины» содержит реальные переходы к доступным магазинам. Сводные показатели разрешены только по собственным магазинам пользователя; для менеджера/кассира отображается выбор, без запроса owner-only отчётов. Одна и та же оболочка используется во всех случаях.

## Меню

В контексте платформы:

- Обзор.
- Партнёры.
- Модерация товаров.
- Аудит.

В контексте магазина страницы сгруппированы по работе:

- Продажи: касса, смена, история продаж, интернет-заказы.
- Каталог: товары и печать этикеток; категории и создание/сканирование товара доступны по существующим ролям.
- Склад: приёмка и инвентаризация — владелец/менеджер.
- Управление: витрина, сотрудники и отчёты — только владелец; уведомления — все участники магазина.

История называется «Продажи и возвраты» для владельца и «Продажи» для остальных: возвраты остаются действием владельца. Права не расширяются ради единообразия меню. Прямое открытие запрещённого раздела показывает ясный отказ; API продолжает проверять права независимо от UI.

Переключатель заменяет повторяющиеся ссылки «Кабинет платформы», «Администрирование» и «Мои магазины», которые сейчас соединяют разные оболочки. Кнопка выхода находится в одном постоянном месте.

## Вход и адреса

`/seller` становится единой точкой входа в рабочий кабинет:

1. Без сессии — форма входа.
2. После обычного входа администратора — `/platform/admin`.
3. Для единственного магазина владельца/менеджера — `/seller/:shopId/products`.
4. Для единственного магазина кассира — `/seller/:shopId/pos`.
5. При нескольких магазинах у пользователя без роли администратора — страница выбора в общей оболочке.
6. Без доступных магазинов и без прав платформы — сообщение «Доступ к магазину пока не выдан» в той же оболочке, с выходом.

Страница нескольких магазинов имеет явный адрес `/seller?view=shops`, чтобы её можно было открыть независимо от обычного редиректа администратора. `/seller#partner-shops` перенаправляется к этой странице при нескольких магазинах, иначе к допустимому начальному разделу.

Существующие `/seller/:shopId/...` и `/platform/admin` сохраняются. Вложенные страницы товаров, заказов, продаж и возвратов сохраняют адреса. Разделы платформы записываются в query: `section=overview|applications|products|audit`; отсутствие или неизвестное значение означает обзор. «Все заявки» и «Все товары» используют ту же навигацию.

URL определяет текущий контекст и раздел. Обновление страницы, назад/вперёд и прямая ссылка сохраняют выбранный раздел. Не вводится сохранённый в localStorage выбор, который мог бы подменить права или привести к чужому магазину после смены аккаунта.

Если вход был вызван открытием защищённой ссылки, после входа возвращаемся на разрешённую внутреннюю страницу. Разрешены только известные рабочие маршруты текущей платформы и магазины из `user.shops`; внешние URL, страницы чужих магазинов и запрещённые роли не становятся адресом возврата. При недопустимом адресе используем обычный начальный раздел по роли.

В непустом меню ровно один пункт имеет `aria-current="page"`. Наведение отличается от активного пункта, чтобы пользователь не видел две одинаково выделенные страницы.

## Архитектура и границы

Общая оболочка и описание контекстов находятся в `apps/web/src/layout`. `App.tsx`, форма входа, кабинет платформы, кабинет магазина и выбор магазинов используют общий маршрутизатор входа и оболочку. Содержимое рабочих страниц, API-запросы и компоненты AdminKit переиспользуются.

У платформы содержимое выбранного раздела остаётся в AdminPage; сама навигация и верхняя панель переходят в WorkspaceShell. Состояние раздела платформы синхронизируется с URL вместо отдельного `useState`, которое сейчас сбрасывается при обновлении.

Не нужны новые зависимости, изменения базы, новая система ролей или новые публичные endpoints. Не меняются расчёты денег, остатки, идемпотентность, выдача заказов, модерация, Gmail и фискализация. Публичная витрина остаётся отдельной покупательской частью; из рабочего кабинета к ней выполняется переход документа в Next.js.

## Проверка готовности

- Один аккаунт с `platformAdmin=true` и одним собственным магазином входит в платформу, переключается в свой магазин и обратно; бренд, профиль и оболочка остаются общими.
- Владелец одного магазина входит сразу в товары без промежуточной панели партнёра.
- Менеджер входит в доступный магазин, кассир — в кассу; owner-only страницы и чужие магазины недоступны.
- Несколько магазинов: правильные имена/роли, корректное переключение, обзор только разрешённых данных. Администратор без memberships получает платформу, пользователь без прав — понятный пустой экран.
- Обновление, назад/вперёд и прямые ссылки сохраняют контекст/раздел; адрес возврата после входа не допускает внешний URL или запрещённый магазин.
- В меню один активный пункт; hover визуально отличается. Длинные имена и email не расширяют экран.
- Проверены 360/768/1024/1440 px, клавиатура, выход, отдельная прокрутка и печать этикеток.
- Проходят форматирование, typecheck, build, API/UI тесты и браузерные сценарии денег/склада/ролей/навигации. Тестовые входы переиспользуют проверяемые fixture-сессии без ослабления production limiter.

Реализация выполняется в этой задаче; после локальной проверки создаётся PR. CI не ожидается по ранее заданной инструкции пользователя. Слияние и deployment не выполняются автоматически.
