# Проверка резервной копии и локальной нагрузки

Дата: 17 октября 2026. Среда: MacBook Air (MacBookAir10,1), macOS 26.5, 8 CPU, 8 GiB RAM; Node.js 24.19.0; отдельный локальный контейнер PostgreSQL 18.6 `mystore-hours-postgres` без заданных Docker-лимитов CPU/RAM. Рабочая база, Render и реальные магазины не использовались.

## Backup и restore

Источник — существующая тестовая база `mystore_permissions_browser_test`, целевая база — новая `mystore_ops_restore_test`. Перед запуском проверено, что целевая база отсутствует; исходная база не изменялась. В тестовом источнике были 6 магазинов, 7 вариантов, 15 движений склада, 5 продаж, 1 онлайн-заказ, 9 записей оплат, 5 строк продаж и 4 возврата.

Команды для повтора в том же локальном окружении:

```bash
set -euo pipefail
docker exec mystore-hours-postgres pg_dump -U mystore -Fc --no-owner --no-acl \
  --dbname=mystore_permissions_browser_test > /tmp/mystore-ops-backup-rehearsal.dump
docker exec mystore-hours-postgres createdb -U mystore mystore_ops_restore_test
docker exec -i mystore-hours-postgres pg_restore -U mystore --exit-on-error \
  --no-owner --no-acl --dbname=mystore_ops_restore_test \
  < /tmp/mystore-ops-backup-rehearsal.dump
docker exec -i mystore-hours-postgres pg_restore --list \
  < /tmp/mystore-ops-backup-rehearsal.dump > /tmp/mystore-ops-backup-contents.list
```

Перед началом проверьте, что `mystore_ops_restore_test` отсутствует: `createdb` намеренно завершает процедуру ошибкой, если база уже существует. `set -euo pipefail` останавливает блок при ошибке любой команды.

Выгрузка заняла 0,88 с, восстановление — 0,74 с. Файл: 130 211 байт; каталог архива содержит 260 строк; SHA-256 `3c9fbf74dd64a25f58f2eaba7c1108490ce87938fb88cbe58e0fe1d89406930b`. `pg_restore` завершился с `--exit-on-error`; до применения новых миграций все перечисленные выше количества совпали с источником. После запуска `npm run migration:run --workspace apps/api` на восстановленной базе миграций стало 24; соединение приложения прошло успешно.

Сборка API прошла. Поднятый локальный API вернул HTTP 200 на `/api/health/ready` (`ok=true`, `database=true`) и HTTP 200 на `/api/public/products?page=1&pageSize=20`. В таблице `migrations` восстановленного снимка до применения кода было 19 записей; миграции приложения обновили её до 24. В тестовой очереди оставались 2 outbox-события, поэтому это наблюдение не является проверкой production-очереди.

API запущен командой `PORT=31401 DATABASE_URL='<connection string для mystore_ops_restore_test>' npm run start --workspace apps/api` из корня репозитория после `npm run build`. `DATABASE_URL` задавался только для локальной восстановленной тестовой базы; значение подключения в отчёт не включено.

## Нагрузочный прогон

Повторяемая команда для локального API:

```bash
LOAD_URL='http://127.0.0.1:31401/api/public/products?page=1&pageSize=20' \
LOAD_DURATION_SECONDS=30 LOAD_REQUESTS_PER_SECOND=50 LOAD_CONCURRENCY=200 \
  node scripts/ops-load-probe.cjs
```

Результат 30-секундного прогона на восстановленной тестовой базе:

| Показатель                            | Результат |
| ------------------------------------- | --------: |
| Запросы                               |     1 500 |
| Частота                               |   50,02/с |
| HTTP 200                              |     1 500 |
| Ошибки сети / HTTP                    |     0 / 0 |
| Фактический пик запросов одновременно |         3 |
| p50                                   |  10,88 мс |
| p95                                   |  16,05 мс |
| p99                                   |  22,50 мс |
| Максимум                              |  61,49 мс |

Команда `node --test scripts/ops-load-probe.test.cjs` прошла 9/9 проверок, в том числе блокировку редиректов, ограничение времени выдачи запросов, отсутствие всплесков после задержки event loop и обнаружение оборванного тела ответа. Пробник читает тело ответа полностью; поэтому задержка включает загрузку тела, а ошибки чтения считаются сетевыми. Защита отказала удалённому URL до отправки запросов. Предел задан в 200 одновременных запросов, но фактический максимум составил 3: при этой частоте и скорости ответа такой прогон не создаёт 200 активных сессий.

## Что этот прогон подтверждает и чего не подтверждает

- Подтверждено чтение custom dump, восстановление в отдельную пустую базу, совпадение контрольных количеств до миграций и запуск миграций текущего приложения.
- Размер тестовой базы мал: 6 магазинов и 7 вариантов; профиль не эквивалентен 100 магазинам и 100 000 вариантам. Локальная проба не подтверждает производительность production, 200 одновременных активных сессий, параллельные продажи/заказы или показатели p95 записи.
- PITR/WAL, расписание и хранение резервных копий, алерты, целевые RPO ≤ 1 часа и RTO ≤ 4 часов не проверялись; для этого нужен доступ к настройкам и метрикам провайдера БД.
- Инструкции по ККМ и принтеру остаются зависимыми от выбора провайдера, модели устройства, ОС и способа подключения.
