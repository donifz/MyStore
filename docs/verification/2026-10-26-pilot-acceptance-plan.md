# MyStore — контрольный план подготовки торгового пилота

Дата: 26 октября 2026. Ответственный: владелец продукта и команда.
Статус: **чек-лист непроверенных операций; успешные результаты сюда заносятся после реальных испытаний**.

## 1. Единый товар и первичная приёмка (программные проверки)

- [ ] «Товары» → «Добавить товар» и «Приёмка» → «Создать товар» открывают одну форму, в том числе для вариантов с `parentId`.
- [ ] Название, цена продажи, фотография, категория, штрихкод, количество и закупочная цена заполняются на одном экране.
- [ ] Пустой штрихкод приводит к генерации уникального внутреннего кода сервером; существующий код не заменяется.
- [ ] Сведения о количестве и себестоимости валидируются **до** создания карточки.
- [ ] Успешный приход формирует движение и увеличивает остаток ровно один раз.
- [ ] Ненадёжная сеть, повтор POST, закрытие вкладки, повторный вход, два пользователя и конфликт штрихкодов не создают повторные товар или приход.
- [ ] Кассир не получает доступ к приёмке. Стоимость закупки не раскрывается в публичном магазине.
- [ ] После проведения доступны штрихкод и печать этикетки через существующие разделы.

## 2. Кассовый E2E

- [ ] Открыть смену с разменом, отсканировать товар, повторить сканирование, вручную изменить количество.
- [ ] Провести наличную оплату, проверить сдачу и отражение выручки только на сумму продажи.
- [ ] Провести оплату картой как **внешнюю отметку**, без ложного утверждения о банковском эквайринге.
- [ ] Протестировать скидку с причиной и ограничениями прав, частичный возврат годного товара и брак.
- [ ] Сверить физический остаток, резерв, движения, прибыль по исходной себестоимости, наличные в смене и отчёты.
- [ ] При обрыве связи повторять исходную операцию с тем же ключом, не создавать вторую продажу.
- [ ] Закрыть смену, проверить ожидаемую и фактическую кассу, обязательный комментарий при расхождении.

## 3. Аппаратная приёмка — нужна реальная техника

- [ ] Зафиксировать ОС/версию браузера, модель/прошивку USB HID-сканера и принтера 58×40 мм, интерфейс подключения.
- [ ] Проверить ведущие нули и форматы EAN-8, EAN-13, Code128; суффикс Enter; переключение раскладки; многократный быстрый скан.
- [ ] Печать одной и нескольких этикеток с точными полями, геометрией и штрихкодом, который повторно считывается.
- [ ] Зафиксировать сценарии отсутствия бумаги, отсоединения и повторной печати. Фоновую печать не считать готовой без локального агента.
- [ ] Снять фото/видео и журнал результатов: дата, устройство, версия ПО, шаги, ожидание, факт, дефект.

## 4. Фискальная ККМ — внешняя зависимость

- [ ] Выбрать провайдера ККМ, подтвердить требования Кыргызстана, получить песочницу/документацию и тестовые ключи.
- [ ] Спроектировать журнал состояния фискализации, идентификатор чека, идемпотентные повторы и обработку ошибочного ответа.
- [ ] Проверить продажу, возврат, сбой сети и кассовую смену на тестовых устройствах провайдера.
- [ ] Не выдавать нефискальный товарный чек за фискальный до успешной интеграции.

## 5. Эксплуатация и нагрузка

- [ ] Отдельная тестовая БД, резервная копия и **измеренное восстановление**; документировать RPO/RTO и собственника резервирования.
- [ ] Проверить PITR у провайдера, хранение копий вне основного диска, мониторинг, доступы и уведомления о сбоях.
- [ ] Нагрузочные сценарии параллельной кассы, конкурентной последней единицы, 10–50 тыс. товаров, пиковых заказов и возвратов.
- [ ] Запустить полный API/Web Vitest, Playwright на 390/768/1440, SSR-тест, `npm run format:check`, `npm run typecheck`, `npm run build`.
- [ ] Провести пилот на 3–5 магазинах и документировать реальные дефекты перед коммерческим запуском.

**Примечание:** этот документ — план проверки, не отчёт о её прохождении. Точные условия, модели устройств, провайдер ККМ и production-инфраструктура требуют решений владельца проекта.
