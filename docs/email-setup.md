# SMTP, сотрудники и восстановление доступа

Для бесплатного Render и Gmail используйте [Gmail API внутри существующего сервиса](gmail-setup.md). Инструкция ниже описывает альтернативный SMTP с отдельным worker.

## Что подключается

MyStore отправляет приглашения сотрудников и партнёров, ссылки восстановления пароля, уведомления о новых заказах и модерации. Покупатель получает статус своего заказа, если указал необязательный email при оформлении. SMS и банковские платежи в этот модуль не входят.

Письма появляются в PostgreSQL очереди в той же транзакции, что и бизнес-изменение. Отправляет их отдельный процесс. API не выполняет SMTP-запросы и сохраняет работу кассы при недоступной почте.

## Настройки

Задайте переменные на API и worker. API проверяет полноту SMTP-настроек без подключения, чтобы показывать готовность конфигурации; сетевое подключение выполняет только worker.

| Переменная                 | Значение                                                                    |
| -------------------------- | --------------------------------------------------------------------------- |
| EMAIL_ENABLED              | `true` для включения worker                                                 |
| PUBLIC_BASE_URL            | Точный origin сайта, например `https://store.example.com`, без пути и query |
| SMTP_HOST                  | Адрес вашего почтового сервера                                              |
| SMTP_PORT                  | Обычно 465 для TLS или 587 для STARTTLS; проверьте настройки сервера        |
| SMTP_SECURE                | `true` для TLS с начала подключения; `false` для STARTTLS                   |
| SMTP_USER                  | SMTP-логин; можно опустить для доверенного локального relay                 |
| SMTP_PASSWORD              | Пароль SMTP; не сохранять в Git                                             |
| SMTP_FROM                  | Разрешённый сервером адрес отправителя                                      |
| EMAIL_TOKEN_ENCRYPTION_KEY | 32 случайных байта в base64, одинаковые на API и worker                     |
| DATABASE_URL               | Одна и та же база API и worker                                              |
| SESSION_SECRET             | Существующий секрет приложения, одинаковый на обоих процессах               |

Создайте собственный ключ шифрования:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

В production требуется HTTPS для PUBLIC_BASE_URL. SMTP с SMTP_SECURE=false требует успешного STARTTLS и проверки сертификата; отключение TLS-проверки не предусмотрено. Не используйте ключи из тестов.

SMTP_FROM должен быть разрешён вашим провайдером; настройте домен отправителя по его инструкции (SPF/DKIM). Настройки и секреты провайдера подключаются в окружении, не через страницу магазина.

## Запуск

Последовательность релиза: применить миграции → запустить API → включить worker из того же собранного image. Обновление production здесь не выполняется автоматически.

```bash
npm run build
npm run migration:run --workspace apps/api
npm run worker:email --workspace apps/api
```

Worker можно запустить отдельным процессом или отдельным сервисом с общей DATABASE_URL. На Render это отдельный background worker с той же версией image и командой `node apps/api/dist/scripts/email-worker.js`. Не запускайте миграции из нескольких worker одновременно.

При EMAIL_ENABLED, отличном от true, worker сообщает disabled и не отправляет письма. При включённой отправке неправильные настройки вызывают ошибку запуска. Без ключа шифрования приглашения сотрудников не создаются; форма восстановления сохраняет нейтральный ответ для существующего и неизвестного аккаунта. После подключения почты нужно повторно запросить восстановление.

Задержанные письма с действующими ссылками могут отправиться при включении worker; отменённые и истёкшие ссылки отменяются. Исторические события заказов и модерации, существовавшие до этой миграции, не рассылаются.

## Работа владельца

В разделе «Сотрудники» владелец приглашает менеджера или кассира по email. Ссылка действует 7 дней. Повторная отправка выдаёт новую ссылку и отменяет предыдущую. Существующий пользователь принимает приглашение после входа под той же почтой; пароль его аккаунта не меняется.

Владелец может изменить роль или отключить доступ. Если сотрудник держит открытую смену, сначала закройте её. Доступ к другим магазинам, пользователь и история операций сохраняются. Управлять владельцами через этот экран нельзя.

В «Уведомлениях» доступны настройки писем для своей почты. Владелец также видит последние отправки магазина и может повторить неудачное уведомление. Приглашения с очищенным секретом нужно выслать заново из «Сотрудников», восстановление запросить заново; их нельзя повторно отправить как обычное уведомление.

Восстановление: «Забыли пароль?» → письмо → новый пароль минимум 12 символов. Ссылка действует 30 минут, используется один раз; новый запрос отменяет старую ссылку. После смены пароля все старые сессии завершены и нужен новый вход.

## Состояния и повторы

«Принято SMTP» означает, что почтовый сервер принял письмо. Это не подтверждение доставки во входящие. Ошибки повторяются через 1, 5, 15, 60 и 240 минут; после шестой ошибки отправка становится failed. Каждое письмо имеет постоянный Message-ID. При потере ответа SMTP или падении процесса после приёма возможен дубль; exactly-once доставка не обещается.

Worker выбирает задания через lease, поэтому два процесса не обрабатывают одно действующее задание одновременно. Зависшие задания доступны после истечения аренды. SIGTERM прекращает новые задания и завершает текущую отправку. Контролируйте долгие pending/sending, failed, логи worker и поля emailPending/emailFailed/emailOldestSeconds в `/api/health/ready`.

Уведомления хранят только номер/статус заказа и результат модерации, без закупочной стоимости и кассовых итогов. Ссылки приглашений и восстановления шифруются, затем удаляются из доставки после отправки, отмены, истечения или окончательной ошибки. В таблице проверок остаётся только хеш токена.

## Ротация ключа

Не заменяйте ключ при существующих зашифрованных pending/sending. Сначала запретите новые запросы приглашений/восстановления на время обслуживания, дождитесь опустошения чувствительной очереди и остановите worker. При ошибках отмените соответствующие приглашения/запросы, очистите их зашифрованные доставки через контролируемую процедуру обслуживания и выдайте новые после смены ключа. Обновите ключ одновременно на API и worker, затем включите обработку. Старые encrypted_payload нельзя расшифровать новым ключом.

## Проверка

Тесты используют отдельные базы с суффиксом `_test` и локальный SMTP fixture. Они не требуют рабочего SMTP и не отправляют письма людям. Проверяют права, изоляцию магазинов, конкурентное принятие/сброс, отзыв сессий, повторы очереди, реальный SMTP протокол и сценарии браузера на 390/1440 px.

После подключения рабочего SMTP отдельно отправьте контрольное приглашение на свою почту и проверьте домен отправителя, «Спам» и переход по HTTPS-ссылке. Только такая проверка подтверждает работу конкретного провайдера.
