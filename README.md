# MyStore

Маркетплейс с общим каталогом продавцов, товарным учётом и кассой. Реализованы учётное ядро, кабинет продавца, USB-сканирование, смены, продажи/возвраты и публичные витрины с общими остатками. Доступны корзина, онлайн-заказы, резервы и модерация товаров.

## Публичный магазин

Главная / — каталог для покупателей. /shops — магазины, /shop/:slug — отдельная витрина (прежние ссылки /shops/:slug автоматически перенаправляются). В футере — «Стать партнёром» и вход для продавцов. Магазины скрыты по умолчанию: владелец включает публикацию в кабинете, в разделе «Витрина». Покупатель оформляет заказ в корзине; самовывоз и доставку согласует с продавцом.

## Кабинет продавца

После запуска базы, миграций и demo seed (инструкции ниже), запустите API и веб в разных терминалах:

```bash
npm run dev --workspace apps/api
npm run dev:web
```

Откройте http://localhost:5173/seller. WEB_ORIGINS должен содержать точный origin браузера. Vite направляет /api к порту3001. Собранный контейнер раздаёт кабинет по /seller на порту3001, включая перезагрузку внутренних маршрутов. Cookie Secure в production требует HTTPS; localhost допустим для локальной проверки.

[Инструкция продавца](docs/seller-guide.md) · [API кассы](docs/api-pos.md) · [Витрины](docs/storefront-guide.md). Есть фото-приёмка и ручная печать этикеток из браузера. Фоновая печать через локальный агент и проверка реального оборудования ещё не реализованы. Обычный USB-сканер передаёт код клавиатурным вводом; физическая модель не проверена.

## Что уже работает

- Вход сотрудников, сессии на 12 часов и выход с отзывом сессии.
- Кабинет продавца, приёмка и касса с USB-сканером, сохранённые черновики.
- Смены, наличные/карта, история и возвраты с исторической себестоимостью.
- Разграничение владельца, менеджера и кассира внутри магазина.
- Создание варианта, генерация внутреннего кода и поиск по заводскому штрихкоду без потери ведущих нулей.
- Приёмка с закупочной стоимостью, остатки и журнал движений.
- Продажа с проверкой текущей цены, наличия и резерва.
- Идемпотентность документов, защита последней единицы от двух продаж.
- Снимки цены и себестоимости продажи, средневзвешенная стоимость запаса.
- Настраиваемый недельный график рабочих часов и часовой пояс магазина с аудитом изменений.
- Расчёт резерва онлайн-заказов на 2 рабочих часа (120 открытых минут) с сохранением срока при повторе запроса.
- Сохранение 30-минутного резерва для ненастроенных магазинов и автоматическое снятие просроченных броней.
- Отображение срока подтверждения заказа в локальном часовом поясе магазина.

Все суммы — целые тыйыны: 15000 означает 150 сом. Количество — целое число от 1 до 1 000 000 000. Документ содержит от 1 до 100 уникальных вариантов.

## Локальный запуск

Нужны Node.js 24.15 или новее в ветке 24.x и Docker Compose. Команды выполняются из корня.

```bash
cp .env.example .env
```

В `.env` задайте случайный `SESSION_SECRET` длиной минимум 32 символа. Для генерации:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Пример пароля PostgreSQL предназначен только для локальной разработки. Если меняете его, обновите также `DATABASE_URL`, `DATABASE_URL_CONTAINER` и `TEST_DATABASE_URL`; в URL используйте URL-кодирование специальных символов.

```bash
npm ci
docker compose up -d db
```

Загрузите переменные `.env` в окружение shell или через свой менеджер окружения. Для приложенного простого файла без пробелов и shell-символов можно использовать:

```bash
set -a
. ./.env
set +a
npm run migration:run --workspace apps/api
```

Создание демо-магазина выполняется только вручную в режиме разработки. Задайте `SEED_PASSWORD` в окружении; минимум 12 символов. Команда не переписывает пароли существующих аккаунтов.

```bash
ALLOW_DEMO_SEED=yes npm run seed --workspace apps/api
npm run dev --workspace apps/api
```

Демо-магазин: `11111111-1111-4111-8111-111111111111`. Аккаунты: `owner@example.test` и `cashier@example.test`; пароль — введённый вами `SEED_PASSWORD`. Не используйте демо-аккаунты в production.

## Запуск API в контейнере

```bash
docker compose up --build -d
```

API доступен на `http://localhost:3001`; база и API привязаны к localhost. Контейнер при запуске выполняет миграции, затем запускает сервер непривилегированным пользователем. Для нескольких production-реплик миграции нужно вынести в отдельный deployment job. Reverse proxy с HTTPS и секреты настраиваются отдельно.

Демо seed блокируется при `NODE_ENV=production`; создайте демо-аккаунты через локальную команду до переключения на контейнерный режим. Новые партнёры регистрируются на /partner; магазин создаётся скрытым.

## Проверки

Интеграционные тесты очищают только выделенную тестовую базу. Их запуск запрещён, если имя базы в `TEST_DATABASE_URL` не заканчивается на `_test`. Не указывайте рабочую базу или production-кластер.

```bash
docker compose exec db createdb -U mystore mystore_test
npm run format:check
npm run typecheck
npm run build
npm test
```

Тесты запускаются последовательно с настоящим PostgreSQL. В CI используются Node.js 24 и PostgreSQL 18; также собирается Docker image и проверяется HTTP-сценарий внутри контейнера. Локально первые 40 проверок выполнены на PostgreSQL 18.4. Тесты включают конкурентные продажи, повтор одинакового ключа и изоляцию магазинов.

## Сканер и интерфейсы

Обычный USB-сканер передаёт код в форму ноутбука как клавиатура с Enter. API ищет товар по этому строковому коду, принимает приход и проводит продажу. Кабинет поддерживает сканирование, черновики и подтверждение получения денег. Этикетки можно просматривать и печатать вручную через браузер; подключение локального агента и проверка оборудования остаются следующими задачами.

## Ограничения текущей версии

Доступны фото-приёмка, корзина, онлайн-заказы и управление резервами. Онлайн-эквайринг и production-адаптер ККМ ещё не подключены. Модерация и ручная печать этикеток реализованы. Партнёры самостоятельно публикуют витрины после заполнения контактов. Email и телефон пока не подтверждаются внешним провайдером. Старый товарный endpoint продажи не создаёт запись оплаты; новый /pos/sales атомарно связывает продажу, смену и ручную отметку получения денег.

Далее — интеграция оборудования и онлайн-оплата. Публичные API читают остатки из того же учёта без копирования; браузер обновляет наличие каждые 5 секунд при исправной сети и при возврате в окно. Внутренние уведомления и outbox реализованы. SMTP-письма обрабатывает отдельный worker после настройки почты.

## Браузерные проверки

После сборки нужен запущенный API со статикой и отдельная база с именем, заканчивающимся на _test. Перед тестами браузера миграции должны быть применены. DATABASE_URL сервера и TEST_DATABASE_URL тестов должны указывать на эту же выделенную базу.

```bash
npx playwright install chromium
npm run build
# В отдельном терминале, с переменными выделенной тестовой базы:
node apps/api/dist/scripts/migrate.js
node apps/api/dist/main.js
# После готовности сервера:
E2E_BASE_URL=http://localhost:3001 npm run test:e2e --workspace apps/web
```

Браузерная подготовка очищает shops/users с CASCADE исключительно в выделенной тестовой базе. Не запускайте её на рабочем кластере. CI создаёт отдельную mystore_browser_test и проверяет сценарий против production image. E2E_BROWSER_PATH допускает явный путь к Chromium в ограниченном тестовом окружении; обычно эта переменная не нужна.

## Заказы и фото-приёмка

Покупатель добавляет товар в корзину одного магазина, указывает контакты и самовывоз/доставку. Оплата — при получении, доставка согласуется отдельно. Новый заказ резервирует остаток на 30 минут до подтверждения. Кабинет «Заказы» позволяет подтвердить, подготовить, отменить и выдать заказ. Выдача создаёт продажу и запись cash/card в собственной открытой смене; согласованная цена сохраняется. Неподтверждённые резервы очищаются при старте и каждую минуту.

Кнопка «Скан / фото товара» доступна владельцу и менеджеру. На телефоне выбор фото предлагает камеру, на ноутбуке можно выбрать снимок. Введите название, закупочную/продажную цену и количество; проверьте карточку и подтвердите. Одновременно создаются товар, артикул, штрихкод и приход. Автоматического распознавания названия/цен нет. Фото сохраняется в PostgreSQL как JPEG до 512 КБ, без метаданных, и показывается в опубликованной витрине. Стандартный USB-сканер можно использовать для ввода существующего штрихкода. При обрыве связи повтор сохранения использует прежние данные и ключ; не создавайте новую карточку до проверки результата.

Публичные квитанции не содержат контактов покупателя; браузер хранит только корзину и случайный ключ квитанции. Для восстановления неизвестного результата откройте корзину и нажмите «Проверить заказ». Секрет квитанции не передаётся через URL.

На Render приложение доверяет только последнему hop заголовка X-Forwarded-For (при системной переменной RENDER=true); локально пересланные IP игнорируются. При старте просроченные новые заказы освобождаются до приёма HTTP-запросов, по одному заказу в транзакции. Оформление дополнительно освобождает просроченные резервы выбранного магазина.

## Определение товара по фото

В фото-приёмке кнопка «Определить по фото» предлагает название, описание и категорию. Продавец видит предложение и степень уверенности, применяет его и может исправить поля. Закупочная/продажная цены, количество и штрихкод остаются ручными. Само распознавание не создаёт карточку или документ: сохранение выполняется прежним подтверждением приёмки.

Сервер использует Gemini API; по умолчанию `gemini-3.5-flash-lite`. Новые зависимости, миграции и сервисы хостинга не нужны. Настройте только серверную переменную `GEMINI_API_KEY` в Environment существующего MyStore на Render. `GEMINI_VISION_MODEL` можно задать для смены совместимой модели. Не используйте `VITE_`/`NEXT_PUBLIC_` для ключа и не добавляйте его в git. Создание ключа: https://aistudio.google.com/apikey . Лимиты и оплату API контролирует аккаунт провайдера; подписка ChatGPT не предоставляет этот ключ.

Без ключа форма остаётся доступной, а распознавание выключено. Ошибка, таймаут, нераспознанный товар или неправильный ответ не стирают введённые данные. В API отправляется нормализованное JPEG-фото без метаданных и список категорий своего магазина; контакты, цены и учётные данные продавца не передаются в запросе распознавания. Фото отправляется только при явном нажатии кнопки. Ответ проверяется сервером, не сохраняется автоматически и не выполняется как код.

API владельца/менеджера: `GET /shops/:shopId/variants/photo-assistant` возвращает доступность и категории; `POST` на тот же путь принимает `{photoDataUrl}` и возвращает `{recognized,name,description,category,confidence,warning}`. Категория выбирается из существующих категорий своего магазина (до 100) плюс «Другое»; для нового магазина используется базовый список. Максимум 20 попыток в минуту на пользователя и магазин, две одновременно на процесс, таймаут 25 секунд, ответ провайдера до 64 КиБ. Повторных запросов к провайдеру автоматически нет.

Проверки используют настоящий HTTP API/БД и контролируемые ответы внешнего провайдера; браузер проверяет применение предложения, сохранение после ручного исправления и ручной ввод после ошибки. Реальное качество распознавания и доступность выбранной модели требуют проверки с рабочим ключом на примерах товаров.

## Сотрудники и email

Владелец приглашает менеджеров и кассиров в разделе «Сотрудники», меняет роли и отключает доступ. На входе есть «Забыли пароль?». Приглашения, восстановление и email-уведомления поддерживают Gmail API внутри существующего сервиса (без отдельного worker) либо SMTP с отдельным worker. [Подключение Gmail](docs/gmail-setup.md).
